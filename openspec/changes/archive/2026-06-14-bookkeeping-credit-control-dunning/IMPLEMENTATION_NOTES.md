## Cross-app FK contract (tasks 25, 26, 27)

The change participates in three cross-app FK contracts. None of them require
schema changes in this repo; they are wired by the consumers and verified at
the contract boundary.

### `bookkeeping-document-attachment-integration` (task 25)

Every `DunningRun.evidenceRefs` array entry, `OninbaarAfschrijving.evidenceRef`,
and every `DunningPauseDispute.evidenceRefs[]` MUST be a docudesk or openregister
URI per the shared `bookkeeping-document-attachment-integration` spec. Evidence
is archived for the 7-year retention window already declared on each schema
(`x-openregister-lifecycle.retention.years: 7`).

URI shape examples:

- `docudesk:files/oninb/faillissementsvonnis-2026-04-12.pdf`
- `openregister:DunningRun/<id>:sha256=<hash>`
- `postnl:<barcode>` for PostNL delivery confirmations.

### `bookkeeping-general-ledger` (task 26)

`OninbaarAfschrijving.boekingId` MUST reference a materialised `GLTransaction`
whose lines debit a bad-debt-recovery account and credit the AP/AR control
account per the T1 REQ-JE-007 balanced-transaction pattern. The GL posting is
generated by the existing GL service on the `OninbaarAfschrijving.post`
lifecycle transition; this change does not author the GL service.

### `bookkeeping-btw-aangifte` (task 27)

`OninbaarAfschrijving.btwAangiftePeriode` MUST be pre-set to the next BTW
filing period (e.g. `2026-Q2`) at the moment the `OninbaarAfschrijving` lands
in `posted` lifecycle state. The existing `VATReturnService` picks the
record up on the next return preparation cycle and emits the correction line
per art. 29 OB.

## APTransaction lifecycle (task 12)

`APTransaction` / `ARInvoice` lifecycle additions per REQ-CCD-005 land via
the upstream `bookkeeping-accounts-receivable-core` change. This change adds
the FK `factuurId` shape on every dunning schema so the upstream lifecycle
transitions can reference our records, but does not modify the AR schema
itself (single-author rule per ADR-024).

When the AR core lands, its lifecycle config gains the following transitions:

| From                  | To                    | Trigger                            |
|---|---|---|
| `issued`              | `overdue`             | scheduled-workflow @ today > dueDate |
| `overdue`             | `dunning_stage_1`     | scheduled-workflow @ day 0 post-overdue |
| `dunning_stage_N`     | `dunning_stage_{N+1}` | scheduled-workflow @ day threshold |
| `overdue`/`dunning_*` | `partially_paid`      | bank-reconciliation partial match  |
| `dunning_*`           | `paid`                | bank-reconciliation full match     |
| `dunning_*`           | `disputed`            | operator action — creates a `DunningPauseDispute` |
| `disputed`            | `dunning_*`           | dispute resolved — closes the pause |
| `dunning_*`           | `written_off`         | operator action — creates an `OninbaarAfschrijving` |
| `dunning_*`           | `in_incasso`          | stage-5 INCASSOBUREAU_API POST succeeds |

The `DunningRunExecuteGuard` enforces the pause-aware part of the contract
from this side: while an active pause exists, the AR core's scheduled-workflow
cannot push a new `dunning_stage_*` transition because every emitted
`DunningRun` is rejected before it leaves `lifecycleState=draft`.
