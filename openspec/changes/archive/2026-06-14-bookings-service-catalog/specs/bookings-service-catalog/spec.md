# Spec: bookings-service-catalog

**Status:** proposed
**Scope:** nextcloud-apps (bookings, calendar, resource-planning, scheduling)
**Tier:** T1 (foundational data model)
**Depends on:** none

## ADDED Requirements

### Requirement: REQ-SC-001 Service catalogue SHALL be declared as a single `Service` register, with no parallel app-local service table

The service catalogue MUST be expressed as a new `Service` register in OpenRegister's
global namespace, per ADR-024. No app-local service table (`booking_services`, `services`,
`service_config`, etc.) SHALL exist.

Each service is a document with identification, temporal dimensions (duration, buffers,
prep time), pricing (base price + dynamic flag), categorization, and lifecycle state.
Services are stored once in OR and consumed by all dependent booking, scheduling,
calendar, and resource-allocation specs across the Nextcloud app ecosystem.

#### Scenario: Service catalogue exists as a single canonical register

- **GIVEN** the Nextcloud deployment
- **WHEN** the openregister schema list is queried
- **THEN** exactly one `Service` register MUST exist.

#### Scenario: No parallel service table in any app

- **GIVEN** the Nextcloud codebase post-deployment
- **WHEN** scanned for app-local PHP Mapper classes or database tables naming
  `*_service`, `service_*`, `appointment_service_*`, `booking_*_service`, or
  `services`
- **THEN** no such parallel structures SHALL exist; all service data flows through
  the canonical `Service` register.

### Requirement: REQ-SC-002 The `Service` schema SHALL declare a fixed minimum field set

The `Service` schema MUST declare the following field set with the indicated types, required status, and default values.

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | UUID | Yes | Unique service identifier (generated by OR) |
| `name` | string | Yes | Human-readable service name (e.g., "Haircut", "1-hour consultation") |
| `code` | string | Yes | Stable slug identifier per administration (e.g., "haircut", "consult-1h") |
| `description` | string | No | Detailed service description for UI display |
| `duration` | integer ≥ 0 | Yes | Service duration in minutes; 0 for non-scheduled services (subscriptions, products) |
| `prepareTime` | integer ≥ 0 | Yes (default 0) | Setup/preparation time in minutes (applied before service start) |
| `bufferBefore` | integer ≥ 0 | Yes (default 0) | Gap (in minutes) required before this service begins (e.g., travel time between locations) |
| `bufferAfter` | integer ≥ 0 | Yes (default 0) | Gap (in minutes) after this service ends (e.g., room turnover, cleaning, travel to next appointment) |
| `basePrice` | decimal ≥ 0 | Yes | Base unit price in the specified currency; used if `dynamicPricing = false` |
| `currency` | string (ISO 4217) | Yes | Currency code; default EUR for Dutch organizations |
| `dynamicPricing` | boolean | Yes (default false) | Flag: if true, dependent pricing specs MUST compute actual price via rules; if false, basePrice is final |
| `serviceCategory` | string | Yes | Category grouping (e.g., "Hair Services", "Consulting", "Catering", "Subscriptions") |
| `resourceTypeRef` | string | No | FK or reference to resource type (skill, room, staff specialty, or generic resource class); resolved by dependent specs |
| `status` | enum | Yes | One of `draft`, `active`, `archived` |
| `administrationId` | string | Yes | FK to administration for multi-tenant isolation |

Schema.org annotation: `schema:Service`.

#### Scenario: Schema validator accepts a minimal service

- **GIVEN** the schema
- **WHEN** `{name:"Haircut", code:"haircut", duration:30, basePrice:25.00, currency:"EUR", serviceCategory:"Hair", status:"active", administrationId:"adm-1"}` is saved
- **THEN** validation MUST pass.

#### Scenario: Negative durations and buffers are rejected

- **GIVEN** a service with `duration: -10`
- **WHEN** the service is saved
- **THEN** validation MUST fail with a "duration must be ≥ 0" error.

#### Scenario: Service code is unique per administration

- **GIVEN** a service with `code: "haircut"` exists in administration `adm-1`
- **WHEN** another service is created with the same code in the same administration
- **THEN** the save MUST fail with a "duplicate service code" uniqueness error.

### Requirement: REQ-SC-003 Service temporal dimensions SHALL be validated with Dutch SMB semantics

Temporal field validation MUST follow:

- **`duration`**: MUST be > 0 for scheduled services (booking slots depend on duration);
  MAY be 0 for non-scheduled products (subscriptions, one-time purchases).
- **`prepareTime`**: MUST be ≥ 0; represents setup before the service (e.g., room
  setup, sterilization, equipment prep). Total calendar block = `prepareTime + duration + bufferAfter`.
- **`bufferBefore`**: MUST be ≥ 0; gap before service start (e.g., travel between locations,
  recovery time). TYPICALLY 0 for collocated resources, > 0 for mobile/traveling staff.
- **`bufferAfter`**: MUST be ≥ 0; gap after service end for turnover (e.g., salon chair
  turnover 15 min, consultation room prep 10 min). Dutch SMB default: 15 min for high-turnover
  services (salons), 0 for low-turnover (consulting).

#### Scenario: Salon haircut with realistic buffers

- **GIVEN** a service definition for "Salon Haircut"
- **WHEN** saved with `{duration:30, prepareTime:5, bufferBefore:0, bufferAfter:15}`
- **THEN** validation MUST pass; **AND** dependent specs MUST interpret total calendar
  block = 5 + 30 + 15 = 50 minutes.

#### Scenario: Consulting call with travel buffer

- **GIVEN** a consultant-visit service
- **WHEN** saved with `{duration:60, prepareTime:0, bufferBefore:15, bufferAfter:15}`
- **THEN** validation MUST pass; **AND** dependent specs MUST schedule the next slot
  ≥ 15 + 60 + 15 = 90 minutes after this one starts.

#### Scenario: Subscription (non-scheduled) is valid with 0 duration

- **GIVEN** a subscription service
- **WHEN** saved with `{name:"Monthly Plan", duration:0, prepareTime:0, bufferBefore:0, bufferAfter:0}`
- **THEN** validation MUST pass.

### Requirement: REQ-SC-004 Pricing SHALL support both fixed and dynamic models via a flag

The `Service` schema MUST declare:

- **`basePrice`**: Fixed unit price. Mandatory, ≥ 0. If `dynamicPricing = false`, this is
  the final price; if `dynamicPricing = true`, this is a reference/fallback only.
- **`dynamicPricing`**: Boolean flag (default false). If true, dependent pricing specs
  MUST compute actual price via time-of-day, volume, surge, or other rules. Dependent specs
  define their own pricing rules in separate registers (e.g., `PricingRule`, `SurgePrice`,
  `VolumeDiscount`); the `Service` register is NOT modified.

#### Scenario: Fixed-price service

- **GIVEN** a service with `basePrice: 25.00, dynamicPricing: false`
- **WHEN** a booking system queries the service
- **THEN** the booking system MUST treat `basePrice` as final; no further pricing-rule
  lookup is required.

#### Scenario: Dynamic-price service signals complexity ahead

- **GIVEN** a service with `basePrice: 100.00, dynamicPricing: true`
- **WHEN** a booking system queries the service
- **THEN** the booking system MUST look up pricing rules in a dependent pricing-rule spec
  (T2+); `basePrice` MUST NOT be used as final price without rule application.

### Requirement: REQ-SC-005 Service SHALL declare a minimal lifecycle: draft → active → archived

`Service` MUST declare a status with three valid states:

| State | Meaning |
|---|---|
| `draft` | Service is incomplete or under development; NOT bookable |
| `active` | Service is live and bookable; visible in catalogs |
| `archived` | Service is retired; retained for historical/audit purposes; NOT bookable |

Transitions:
- `draft → active`: Operator or system action; no guards.
- `active → archived`: Operator action; no guards. Archived services remain queryable.
- `archived → active`: Allowed for restoration.

#### Scenario: Draft service is not bookable

- **GIVEN** a service with `status: draft`
- **WHEN** a booking system queries available services
- **THEN** the service MUST NOT be included in the bookable catalog.

#### Scenario: Service can transition from active to archived and back

- **GIVEN** a service with `status: active`
- **WHEN** transitioned to `archived`
- **THEN** it MUST NOT be available for new bookings; **AND** it MUST still be
  queryable for historical slot/booking references.

### Requirement: REQ-SC-006 Categorization SHALL be flat in T1; nesting deferred to T2+

Services MUST be grouped via a flat `serviceCategory` field (string). No hierarchical
category register SHALL exist in T1. Nested/hierarchical category management is deferred to T2+.

#### Scenario: Services grouped by category

- **GIVEN** services with `serviceCategory: "Hair Services"` and `serviceCategory: "Skincare"`
- **WHEN** the booking UI queries by category
- **THEN** the services MUST be grouped and displayed correctly; hierarchy is not
  required (flat list suffices for T1).

### Requirement: REQ-SC-007 Service SHALL support resource-type linking for dependent specs

The `Service` schema MUST declare `resourceTypeRef` (string, optional FK). This field
is a forward reference to "resource type" concepts (skill, room, staff specialty, etc.)
defined and managed by dependent specs.

The meaning of `resourceTypeRef` is NOT prescribed in T1:
- Could refer to a skill/specialty (e.g., "hairdresser", "dermatologist")
- Could refer to a room/asset type (e.g., "meeting-room", "studio")
- Could refer to a generic resource class defined in a dependent spec
- Could be null for services with no specific resource requirement

Dependent specs (e.g., `bookings-resource-allocation`, `bookings-availability`) interpret
and validate `resourceTypeRef` according to their own requirements.

#### Scenario: Service linked to a resource type

- **GIVEN** a service with `resourceTypeRef: "hairdresser"`
- **WHEN** a dependent booking spec queries the service
- **THEN** the dependent spec MUST be able to read `resourceTypeRef` and apply its own
  resource-matching logic.

#### Scenario: Service with no resource requirement

- **GIVEN** a service with `resourceTypeRef: null` (e.g., a subscription or product)
- **WHEN** a dependent booking spec processes the service
- **THEN** the dependent spec MUST handle null gracefully; no resource matching required.

### Requirement: REQ-SC-008 Service code SHALL be unique per administration and stable across time

The `code` field MUST uniquely identify a service within an administration. Once assigned,
it MUST NOT change, as dependent specs MAY reference it for mapping, reporting, or
external integrations.

#### Scenario: Service code uniqueness per administration

- **GIVEN** administration `adm-1` with service `{code:"haircut", ...}`
- **WHEN** another service is created in the same administration with `code: "haircut"`
- **THEN** the save MUST fail with uniqueness error; **AND** a different code MUST be
  chosen (e.g., "haircut-v2").

#### Scenario: Same code can exist in different administrations

- **GIVEN** administration `adm-1` with service `{code:"haircut", ...}`
- **WHEN** administration `adm-2` creates a service with `{code:"haircut", ...}`
- **THEN** the save MUST succeed (codes are unique per administration, not globally).
