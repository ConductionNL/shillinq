# Proposal: add-shillinq-consultancy-project-accounting

`kind: config` per ADR-032 — the centre of mass is declarative
schema metadata + manifest entries + RJ-270 stage + rate-card seed
data + period-end `ScheduledWorkflow`. No PHP service classes.

## Summary

Introduce **consultancy project accounting** for Shillinq as a T3
capability per `adr-001-bookkeeping-tier-roadmap.md`. This change
declares the `Project`, `ProjectAssignment`, `RateCard`,
`WipBalance`, and `BillableHour` registers (the last being the
billable-hours extension of `UrenRegistratie`) with
`x-openregister-lifecycle` rules and `x-openregister-calculations`
for RJ 270 / IFRS 15 percentage-of-completion revenue recognition
(per ADR-031), declares the period-end WIP snapshot as an OR
`ScheduledWorkflow`, wires navigation into `src/manifest.json`
(per ADR-024), and ships `rj-270-stages.json` +
`rate-card-templates.json` seeds. No `RevenueRecognitionService`,
no `ProjectPlService`.

This change conforms to the shared
[`nextcloud-app`](../../specs/nextcloud-app/spec.md) spec for app
structure, OpenAPI 3.0 register format, and `ConfigurationService::importFromApp()`
repair-step seeding.

**Depends on:** T1 `bookkeeping-general-ledger` (project P&L
filters GL by project FK; cost-to-cost completion percentage reads
GL cost postings) and T2 `bookkeeping-accounts-receivable-core`
(billable hours invoiced through AR; recognised revenue posts
through AR).

## Motivation

Consultancy is Conduction's own primary customer profile.
Multi-project WIP, billable hours, RJ 270 / IFRS 15 percentage-of-
completion, multi-rate cards, utilisation, project P&L — these
are non-negotiable for a working consultancy administration.
Without project accounting, every Conduction-pattern customer must
run an external project-time-tracking tool — defeating the suite's
value.

The architecture insight is that every project-accounting metric
is a **derived field** (calculations + aggregations) on an existing
schema, not a service-orchestrated computation.

## Scope

### In Scope

- One new capability spec
  (`bookkeeping-consultancy-project-accounting`).
- `Project` register with `(projectNumber, customerId, name,
  state, totalContractValue, totalEstimatedCosts, costsIncurredToDate,
  recognisedRevenue, currency, startDate, endDate, administrationId)`.
- Lifecycle `offerte → active → on-hold → closed → archived`.
- `ProjectAssignment` register linking person + project + rate-card
  + role.
- `RateCard` register with `(level, hourlyRate, currency,
  effectiveFrom, effectiveTo, administrationId)`.
- `WipBalance` register holding period-end WIP snapshots per
  project, generated by an OR `ScheduledWorkflow` triggered by T2
  period close.
- `BillableHour` semantics on `UrenRegistratie` (from sibling
  `add-shillinq-zzp-tax-regime`): `recognisedRate` snapshotted at
  write time per RJ 270 §3.2.4.
- RJ 270 / IFRS 15 percentage-of-completion via
  `x-openregister-calculations` (`recognisedRevenue =
  totalContractValue × costsIncurredToDate / totalEstimatedCosts`).
- Utilisation via `x-openregister-calculations`
  (`billableHoursThisPeriod / capacityHoursThisPeriod`).
- Project P&L via `x-openregister-aggregations` filtering `GLLine`
  by project FK.
- Manifest navigation under `Projecten` (visible for `consultancy`-
  flagged admins).

### Out of Scope

- **Time-and-materials vs fixed-price project nuance** — both
  modelled via the same `Project` schema; mode-specific reporting
  is roadmap.
- **Multi-currency project boundary** — T5.
- **Implementation code** — spec-only change.

## Risks

### Risk 1: Multi-rate boundary (rate-card revisions mid-project)

**Severity**: Low → mitigated
**Mitigation**: Per RJ 270 §3.2.4, hours are valued at the rate-as-
of-performance-date. `RateCard` carries `effectiveFrom` /
`effectiveTo`; `BillableHour.recognisedRate` is snapshotted at
write time per `REQ-CPA-009`.

### Risk 2: Cost-to-cost method assumes accurate `totalEstimatedCosts`

**Severity**: Low
**Mitigation**: Operator-supplied; `totalEstimatedCosts` can be
revised mid-project (audit-trail records the change); recognised
revenue automatically recalculates per `REQ-CPA-007`.

### Risk 3: WIP snapshot cadence vs period close

**Severity**: Low
**Mitigation**: WIP `ScheduledWorkflow` is triggered by T2 period
close events, not a fixed cron — ensures the snapshot reflects the
closed period's final state.

## Rollback Strategy

Spec-only change. Standard rollback: revert the commit; delete the
change folder. After implementation: revert the PR, run the repair
step in down-direction. Registers are non-destructive.
