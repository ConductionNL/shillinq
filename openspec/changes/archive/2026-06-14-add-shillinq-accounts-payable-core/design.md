# Design — Accounts Payable (Core)

**status: pr-created**

## Context

Shillinq's original scope was customer invoicing (AR); AP is the
other half of the operational envelope. Per the legacy AP/AR draft
cluster from intelligence-db (`competitor_features` with
`app_slug=shillinq`), vendor master + AP invoice + payment run are
top-tier customer-asked features.

Per ADR-022, approval routing comes from OR, not from an app-local
table. Per ADR-031, SEPA pain.001 + iDEAL XML composition is a
declarative calculation, not a `SepaService`. This change locks
those decisions into the spec.

The change is **spec-only**. Implementation lands later through
`opsx-apply` and the standard Hydra pipeline; this doc explains
*why* the shape is what it is.

## Goals

- Express the entire AP-core surface as **declarative metadata** —
  schemas + lifecycle + calculations + aggregations + manifest
  entries — per ADR-031.
- Consume OR's approval-workflow abstraction — per ADR-022. Zero
  parallel approval table.
- Make the spec a **competent-bookkeeper readable contract** —
  Dutch SMB AP flow recognisable end-to-end (vendor intake,
  invoice approval, 3-way match where applicable, payment run,
  SEPA XML, GL posting, aging).
- Keep the FK shape conditional so future T4 procurement (PO + GR)
  attaches without destructive migration.

## Non-Goals

- No PHP approval service, no `APInvoiceService.php`.
- No PHP SEPA generator, no `SepaService`.
- No PSD2 live-feed bank initiation — T4.
- No multi-currency translation — T5.
- No VAT/BTW posting automation — T3.

## Decisions

### D1 — AP is a sub-ledger that materialises GL transactions

`APInvoice` is a sub-ledger register carrying the vendor-facing
fields. Posting an AP invoice materialises a balanced
`GLTransaction` per the T1 `JournalEntry` lifecycle pattern. T1's
`GLLine.subLedgerType: "ap"` + `subLedgerRef` (stubbed in T1
REQ-GL-009) resolve to this register.

**Alternative considered**: AP invoice directly writes GL lines
without a separate register. Rejected — sub-ledger separation is
industry-standard for AP aging, approval routing, and audit
queries that should not require GL-line scanning.

### D2 — AP approval routing comes from OR per ADR-022

The AP lifecycle declares `requires` clauses that consume OR's
approval-workflow abstraction (`x-openregister-approval`). No
app-local approval table in shillinq.

**Alternative considered**: A shillinq `ApprovalService` mirroring
Twinfield. Rejected per ADR-022 enumerated anti-pattern.

### D3 — Conditional 3-way match precondition

When PO + Goods Receipt registers are present (future T4
procurement), `APInvoice.post` requires matched quantities + amounts
against the PO and GR. When they are not present, the precondition
reduces to a 2-way match (invoice + manual operator approval). The
FK fields (`poRef`, `grRef`) are declared so future procurement
attaches additively.

If OR's lifecycle engine cannot express conditional preconditions,
ADR-031's exception path applies: a single-method
`OCA\Shillinq\Lifecycle\ThreeWayMatchGuard::matches(...)` ships,
cited in the spec.

### D4 — Payment run is a register, not a service

A `PaymentRun` is a register carrying N selected `APInvoice`
UUIDs + the SEPA pain.001 XML output (generated by an
`x-openregister-calculations` field composing the XML from the
selected invoices' bank details). Operator downloads the XML and
uploads it to their bank portal. iDEAL payment-link generation is
a per-invoice calculation.

**Alternative considered**: A `PaymentService` that orchestrates
selection + XML generation. Rejected per ADR-031 — the calculation
extension covers XML composition; selection is operator-driven
through standard register UI.

Live PSD2 bank initiation is T4.

### D5 — AP aging is an aggregation

`x-openregister-aggregations` query grouping `APInvoice` by
`(vendorId, agingBucket)` where buckets are computed from
`(today - dueDate)` thresholds (0-30 / 30-60 / 60-90 / 90+ days).
`paid` / `voided` invoices excluded.

**Alternative considered**: A PHP `AgingReportService`. Rejected
per ADR-031 — aggregation engine handles GROUP BY + bucket
computation.

## Reuse Analysis

| Capability needed | What already exists | Reuse strategy |
|---|---|---|
| AP invoice lifecycle | OR `x-openregister-lifecycle` (ADR-031) | Lifecycle on `APInvoice` with 3-way match precondition; materialises balanced `GLTransaction` per T1 `JournalEntry` pattern |
| AP approval routing | OR approval-workflow (ADR-022) | Consumed via `x-openregister-lifecycle.requires`; no shillinq approval table |
| SEPA pain.001 XML | OR `x-openregister-calculations` (ADR-031) | XML composition is a calculation field on `PaymentRun.sepaXml`; no PHP service |
| iDEAL link generation | OR `x-openregister-calculations` | Per-invoice calculation field on `APInvoice.idealLink` |
| AP aging | OR `x-openregister-aggregations` | GROUP BY `(vendorId, agingBucket)` excluding paid/voided |
| Materialised GL posting | T1 `JournalEntry` materialisation pattern (REQ-JE-007) | Same lifecycle action shape; emits one balanced `GLTransaction` per posted AP invoice |
| Source-document attachment | T2 `bookkeeping-document-attachment-integration` (FK URI) | `APInvoice.sourceDocumentUri` consumes the contract |
| Vendor master | New T2 register (or OR contact abstraction if stable) | Per ADR-022 review — prefer OR contact if available, else app-local with migration plan |
| Audit trail | T2 `bookkeeping-audit-trail` (OR audit-trail-immutable) | Automatic on lifecycle transitions |
| Manifest navigation | T1 manifest pattern | 4 entries (Vendors, AP, AP Aging, Payment Runs) + their pages |

**Net new code in implementation cycle**: 3 schema declarations + 1
lifecycle block + 2 calculation fields + 1 aggregation + 4 manifest
entry pairs. At most 1 single-method PHP guard
(`ThreeWayMatchGuard`) gated by ADR-031 exception.

## Declarative-vs-imperative decision (per ADR-031)

| Behaviour | Decision | Why |
|---|---|---|
| AP invoice lifecycle | Declarative (`x-openregister-lifecycle`) | Pure state machine |
| AP 3-way match precondition | Declarative if engine supports conditional clauses; else single-method PHP guard (`ThreeWayMatchGuard`) per ADR-031 exception | Resolution in discovery; spec shape-neutral |
| AP approval routing | Consumed from OR approval-workflow | ADR-022 |
| Payment run XML composition | Declarative (`x-openregister-calculations`) | Pure data → string transformation |
| iDEAL link generation | Declarative (`x-openregister-calculations`) | Pure data → string transformation |
| AP aging | Declarative (`x-openregister-aggregations`) | GROUP BY + SUM with date bucket calculations |
| GL materialisation on post | Lifecycle action invoking T1's existing materialisation extension | No new service |
| Source-document attachment | FK URI per T2 `bookkeeping-document-attachment-integration` | ADR-022 |

No service class authored in this envelope (subject to ADR-031
exception: at most one single-method `ThreeWayMatchGuard`).

## Seed Data

None. Vendors + AP invoices are operator-authored on first use; no
templates.

## Risks / Trade-offs

| Risk | Mitigation |
|---|---|
| PO / GR registers not available for 3-way match | Spec is conditional: 2-way match when PO/GR absent; FKs declared so future T4 procurement attaches additively |
| Conditional precondition not declaratively expressible | Single-method `ThreeWayMatchGuard` per ADR-031 exception; remove when OR's engine supports conditional clauses |
| Vendor master overlaps with OR's contact abstraction | Per ADR-022 review during implementing cycle; thin view onto OR contact if stable, else app-local with migration plan |
| Approval routing topology too rigid | Operator-configurable per administration (linear / threshold / hybrid); resolved during implementing cycle's UX review |
| SEPA XML schema versioning | Pin pain.001.001.03 in the spec; coordinate with banks on any future version uplift |

## Migration Plan

Spec-only — no runtime migration in this change. When implementation
lands:

1. `lib/Settings/shillinq_register.json` is patched with the three
   schemas (additive — no existing schema changes).
2. `src/manifest.json` is patched with 4 new menu entries + their
   pages (additive).
3. If 3-way match conditional precondition cannot be expressed
   declaratively, `lib/Lifecycle/ThreeWayMatchGuard.php` ships
   (single method, ~20 LOC, ADR-031 exception annotated).

Down-direction: registers are non-destructive — reverting removes
the manifest entries + lifecycle bindings; AP invoices remain
queryable but unreferenced.

## Open Questions

1. **3-way match conditional shape** — resolved in `opsx-ff`
   discovery; spec shape-neutral.
2. **Vendor master vs OR contact** — resolved per ADR-022 review
   during implementing cycle.
3. **Approval routing topology default** — resolved during
   implementing cycle's UX review.
