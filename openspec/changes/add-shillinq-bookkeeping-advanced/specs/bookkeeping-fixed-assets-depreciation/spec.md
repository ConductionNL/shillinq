# Spec: bookkeeping-fixed-assets-depreciation

**Status:** proposed
**Scope:** shillinq
**Tier:** T4 (advanced engine)
**Depends on:** bookkeeping-general-ledger (T1)

## ADDED Requirements

### Requirement: REQ-FA-001 — The fixed-asset register SHALL be stored as an OpenRegister-managed `FixedAsset` register

The fixed-asset register MUST be declared as a register in
`lib/Settings/shillinq_register.json` per ADR-024, with the
`FixedAsset` schema as the canonical entity. No custom PHP model,
no custom database table, no parallel link table (per ADR-022
anti-pattern list). Depreciation rules and schedules are declared
as schema metadata per ADR-031, not authored as service classes.

#### Scenario: Reviewer confirms no parallel storage

- **GIVEN** the shillinq codebase
- **WHEN** scanned for `lib/Db/` Mapper classes naming `fixed_asset`
  / `assets` / `depreciation`
- **THEN** no such classes SHALL exist; all asset data flows through
  the OR object API.

### Requirement: REQ-FA-002 — The `FixedAsset` schema SHALL declare a fixed minimum field set including schema-declared depreciation rules

The `FixedAsset` schema MUST declare the following fields with the listed required/optional flag (depreciation rules are schema-declared, not service-coded):

| Field | Type | Required | Purpose |
|---|---|---|---|
| `assetNumber` | string | Yes | Operator-assigned unique reference within the administration |
| `name` | string | Yes | Human-readable name (e.g. "Dell laptop XPS-15") |
| `assetCategory` | enum | Yes | One of `buildings`, `vehicles`, `machinery`, `it-equipment`, `furniture`, `intangibles` |
| `acquisitionDate` | date | Yes | Date the asset entered service |
| `acquisitionCost` | number ≥ 0 | Yes | Original cost in the administration's base currency |
| `currency` | string (ISO 4217) | Yes | Currency of the acquisition cost (multi-currency translation per T4 `bookkeeping-multi-currency`) |
| `usefulLifeMonths` | integer ≥ 1 | Yes | Useful life expressed in months |
| `residualValue` | number ≥ 0 | Yes | Estimated value at end of useful life |
| `depreciationMethod` | enum | Yes | One of `linear`, `degressive`, `units-of-production`, `none` |
| `degressiveRate` | number | No | Annual percentage when `depreciationMethod = degressive` (required in that case) |
| `commercialRate` | number | No | Rate used for commercial books (IFRS / Dutch GAAP) |
| `fiscalRate` | number | No | Rate used for fiscal books (Wet IB / Wet VPB) — may differ from `commercialRate` |
| `assetAccountNumber` | string | Yes | FK to the `Account` carrying the asset's gross value |
| `accumulatedDepAccountNumber` | string | Yes | FK to the contra `Account` for accumulated depreciation |
| `depreciationExpenseAccountNumber` | string | Yes | FK to the P&L `Account` for the depreciation expense |
| `disposalDate` | date | No | Date the asset was disposed of (sale, scrap, donation) |
| `disposalAccountingTreatment` | enum | No | One of `sale`, `scrap`, `donation`, `transfer` (required when `disposalDate` is set) |
| `lifecycleState` | enum | Yes | One of `proposed`, `active`, `disposed`, `archived` |
| `administrationId` | string | Yes | FK to the administration owning the asset |

`commercialRate` and `fiscalRate` MAY both be set, allowing the
schedule generator to produce two parallel depreciation streams (per
REQ-FA-004). When `depreciationMethod = none`, no schedule is
generated and no automatic postings happen.

OpenRegister's built-in fields (`id`, `uuid`, `version`, `createdAt`,
`updatedAt`, `owner`, `auditTrail`) are not redeclared.

#### Scenario: A linear-method asset validates with required fields

- **GIVEN** the schema is loaded
- **WHEN** an asset `{assetNumber: "FA-0001", name: "Dell XPS-15", assetCategory: "it-equipment", acquisitionDate: "2026-01-01", acquisitionCost: 2400, currency: "EUR", usefulLifeMonths: 48, residualValue: 0, depreciationMethod: "linear", assetAccountNumber: "0220", accumulatedDepAccountNumber: "0225", depreciationExpenseAccountNumber: "4500", lifecycleState: "active", administrationId: "adm-1"}` is validated
- **THEN** validation MUST pass.

#### Scenario: A degressive asset without `degressiveRate` is rejected

- **GIVEN** the schema
- **WHEN** an asset with `depreciationMethod: "degressive"` and no
  `degressiveRate` is validated
- **THEN** validation MUST fail with a "degressiveRate required for
  degressive method" error.

### Requirement: REQ-FA-003 — Depreciation schedules SHALL be declared as `x-openregister-calculations` on the asset, not generated by a PHP service

The per-period depreciation amount MUST be exposed as an
`x-openregister-calculations` derived field on `FixedAsset` named
`monthlyDepreciation` (linear case) or `currentBookValue` (any
method), computed from the schema fields plus the elapsed time
since `acquisitionDate`. No PHP `DepreciationScheduleService`
materialises a per-month schedule table — the values are derivable
on demand from the asset fields and the current date (per ADR-031
"derived field" pattern, the same `isOverdue` shape decidesk
ActionItem uses).

When a posting is needed (per REQ-FA-005), the OR scheduled-workflow
reads the derived field for the current period and emits the GL
posting; the schedule itself stays implicit.

#### Scenario: `currentBookValue` recomputes correctly after `acquisitionDate`

- **GIVEN** an asset with `acquisitionCost: 2400`, `residualValue: 0`,
  `usefulLifeMonths: 48`, `depreciationMethod: linear`,
  `acquisitionDate: 2026-01-01`
- **WHEN** the derived field is read on `2026-07-01` (6 months
  elapsed)
- **THEN** `currentBookValue` MUST equal `2100` (`2400 – 6 × 50`).

#### Scenario: A `none`-method asset reports `currentBookValue = acquisitionCost` indefinitely

- **GIVEN** an asset with `depreciationMethod: none`
- **WHEN** the derived field is read at any later date
- **THEN** `currentBookValue` MUST equal `acquisitionCost`; **AND**
  `monthlyDepreciation` MUST equal `0`.

### Requirement: REQ-FA-004 — Parallel commercial + fiscal depreciation streams SHALL be supported

When both `commercialRate` and `fiscalRate` are set, the calculated fields MUST expose both streams (e.g. `commercialBookValue`,
`fiscalBookValue`, `monthlyCommercialDepreciation`,
`monthlyFiscalDepreciation`). Each stream MUST post to a separate
sub-account or use a dedicated `bookSet` dimension (per T4
`bookkeeping-cost-centers-dimensions`) so the trial balance can
filter by commercial vs fiscal view.

#### Scenario: Commercial and fiscal book values diverge under different rates

- **GIVEN** an asset with `acquisitionCost: 10000`, `usefulLifeMonths: 60`,
  `commercialRate: 0.20` (5 years), `fiscalRate: 0.33` (3 years)
- **WHEN** the derived fields are read 12 months after acquisition
- **THEN** `commercialBookValue` MUST equal `8000`; **AND**
  `fiscalBookValue` MUST equal `6700` (`10000 × (1 – 0.33)`).

### Requirement: REQ-FA-005 — Monthly depreciation postings SHALL be emitted by an OpenRegister scheduled workflow, NOT by a per-app background job

The monthly run posting depreciation expense for every active asset MUST (per ADR-031 §"Background jobs that walk an object queue and apply a transition" path 2) be implemented as an OpenRegister
`ScheduledWorkflow` entity tying the asset register to an n8n
workflow on a monthly cadence. The workflow MUST iterate active
assets, read the calculated monthly depreciation, and create a
`JournalEntry` of sub-type `recurring` per asset that materialises
the `GLTransaction` (debit depreciation expense, credit
accumulated depreciation). shillinq MUST NOT author a
`DepreciationJob extends TimedJob` PHP class.

#### Scenario: Reviewer confirms no per-app TimedJob

- **GIVEN** the shillinq codebase
- **WHEN** scanned for classes extending `OCP\BackgroundJob\TimedJob`
  in `lib/BackgroundJob/` with method names matching
  `*Depreciation*` / `*RunMonthly*`
- **THEN** no such classes SHALL exist; depreciation runs MUST be
  driven by a `ScheduledWorkflow` record.

#### Scenario: A monthly run posts one journal per active asset

- **GIVEN** 25 active linear-method assets in administration `adm-1`
  and a `ScheduledWorkflow` tying `FixedAsset` → `monthly-depreciation`
  n8n workflow
- **WHEN** the schedule fires for period `2026-07`
- **THEN** 25 `JournalEntry` records of sub-type `recurring` MUST
  be created in state `pending`; **AND** each MUST reference the
  source asset by `sourceAssetId`.

### Requirement: REQ-FA-006 — Asset disposal SHALL be a declarative lifecycle transition that auto-emits the closing journal

The `FixedAsset` schema MUST declare an `x-openregister-lifecycle`
transition `active → disposed` whose action emits a closing
`JournalEntry` for the asset: it credits the asset account for the
remaining gross value, debits accumulated depreciation, posts the
gain or loss to the appropriate P&L account based on
`disposalAccountingTreatment` and the disposal proceeds entered at
transition time. No PHP `DisposeAssetService` orchestrates this —
the transition action is declarative.

#### Scenario: Disposing an asset at proceeds equal to book value emits a zero-gain journal

- **GIVEN** an asset with `currentBookValue: 600` and
  `disposalAccountingTreatment: sale`
- **WHEN** the operator transitions it to `disposed` with proceeds
  `600`
- **THEN** a `JournalEntry` MUST be created that zeroes the asset
  account, zeroes accumulated depreciation, and posts no gain or
  loss; **AND** the asset's `lifecycleState` MUST be `disposed`.

#### Scenario: Disposing at proceeds above book value emits a gain

- **GIVEN** an asset with `currentBookValue: 600`
- **WHEN** disposed with proceeds `750`
- **THEN** the emitted `JournalEntry` MUST post a `150` credit to
  the configured "boekwinst vaste activa" account.

### Requirement: REQ-FA-007 — Fixed assets SHALL be reachable through the shillinq manifest navigation

`src/manifest.json` MUST declare a navigation entry
(`Bookkeeping > Fixed Assets`) with a `type: index` page binding
to the `FixedAsset` register and a `type: detail` page for
individual assets. Both pages MUST be rendered by the generic
`@conduction/nextcloud-vue` `CnIndexPage` / `CnDetailPage`
components driven by manifest config — no bespoke Vue files (per
ADR-024 Tier-4).

#### Scenario: The detail page renders the derived schedule

- **GIVEN** an active linear-method asset
- **WHEN** the operator opens the detail page
- **THEN** the page MUST render the asset fields, the calculated
  `currentBookValue`, `monthlyDepreciation`, projected book value
  at end of useful life, and the disposal action when the
  operator's role allows.
