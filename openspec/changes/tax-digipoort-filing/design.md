# Design: tax-digipoort-filing

Read at shillinq development `79f438f33` and integriq development on
2026-09-27.

## Context

**The port that nothing calls.** `DigipoortSbrAdapterInterface`
(`lib/Service/External/Digipoort/DigipoortSbrAdapterInterface.php`) has
`submit(array $payload): DigipoortSubmissionResult` (line 88) and
`isDormant()` (line 95). `lib/AppInfo/Application.php:477` binds it to
`LogDigipoortSbrAdapter`, which logs. No service calls `submit()`; the CSRD
adapter's docblocks name the port as its future transport.
`lib/Settings/connections.json` (line 5) declares `digipoort-sbr` as
`available: false` with "Nothing reaches Digipoort".

**The filing record.** `XbrlInstance`
(`lib/Settings/register.d/add-shillinq-sbr-xbrl-reporting.json:13`) holds
`entryPoint`, `taxonomyVersion`, `reportingPeriodStart` and `End`,
`sourceStatementId`, `mappingId`, `instanceXml`, `instanceHash`, `state`,
`digipoortReceiptId`, `digipoortSourceSlug`, `submittedAt`, `acceptedAt` and
`rejectionReason`, with lifecycle draft, validated, submitted, accepted,
rejected. None of its transitions has a `requires` or an action. Its
description says it is derived from a posted `FinancialStatement`; nothing
builds one. Pages: `SbrXbrlFilings` and `SbrXbrlFilingDetail`
(`src/manifest.json`, `/sbr-xbrl-filings`). `XBRLTaxonomy` records hold
taxonomy versions with effective and expiry dates (REQ-SBR-002),
`XBRLMapping` maps accounts to concepts (REQ-SBR-004).

**The catalogue.** `lib/Reporting/ReportCatalogue.php` lists `vat-return`
(line 83, generated by `VatReturnReportGenerator` as a plain XML, not an
XBRL instance) and `sbr-xbrl` (line 92, "SBR-jaarrekening in XBRL
(KvK/Belastingdienst)"). `ReportGenerationService` discovers generators by
`reportType()`; none answers `sbr-xbrl`, so it logs "no generator".
`AnnualAccountsReportGenerator` renders the annual accounts document from a
`FinancialStatement`.

**The VAT return.** After `tax-vat-return-from-books`, the prepared
`BtwAangifte` carries its declarations per return box. Its `submit`
transition has no `requires` beyond the checks guard that change adds, and
no action. REQ-VBTW-010 requires the submission to be dispatched to the
`digipoort-sbr` source with no direct HTTP in shillinq; this design meets
that through integriq, the renamed openconnector.

**integriq.** No Digipoort or SBR source exists on integriq development.
Its Peppol connector (`peppol-access-point-connector`) is the pattern: a
leaf app emits `nl.conduction.peppol.outbound.requested` with a
`payloadFileUri`, integriq transmits with retry and dead-lettering, and
emits a delivery status event.

## Goals / Non-Goals

**Goals**

- A VAT return and a set of annual accounts each become a valid XBRL instance, downloadable.
- A submitted filing is one Digipoort accepted, and the page says so with the delivery reference.
- A rejection shows the Belastingdienst or KvK error codes.

**Non-Goals**

- Any network call from shillinq.
- IB, Vpb, ICP and CSRD filings, which reuse the path later.

## Decisions

### D1. Build the instance in shillinq

`VatReturnXbrlBuilder::build(BtwAangifte)` writes the facts of each return
box from the stored declarations, with the administration's (or the VAT
unity's) VAT number and the period, on the OB aangifte entry point of the
`XBRLTaxonomy` record effective for the period.
`AnnualAccountsXbrlBuilder::build(FinancialStatement)` maps balance sheet
and profit and loss through `XBRLMapping` onto the KvK entry point for the
statement's size class. Both write an `XbrlInstance` in draft with
`filingType` (ob-aangifte or kvk-deponering), the XML and its hash.
`SbrXbrlReportGenerator` answers `sbr-xbrl` by returning the annual
accounts instance.

Alternative considered: let integriq build the XBRL from shillinq's
figures. Rejected: the instance is shillinq's statement of its books, and
ADR-091 gives integriq the transport, not the content.

### D2. Validate before submit

`XbrlInstanceValidationGuard` is the `requires` of `validate`: it checks
the instance against its entry point's required concepts, the period, the
identifier and the arithmetic of the totals, and denies with the failing
items. A return whose checks (from `tax-vat-return-from-books`) fail never
reaches this point.

### D3. Hand off on submit, trust only integriq's report

`submit` on `XbrlInstance` declares the action `hand-to-digipoort`, served
by `HandToDigipoortAction`, which stores the XML under
`/Shillinq/Sbr/<administrationId>/` and calls
`DigipoortSbrAdapterInterface::submit()`. With integriq installed that is
`IntegriqSbrHandoffAdapter`, which emits `nl.conduction.sbr.filing.requested`
and returns pending; otherwise the log adapter, and the action refuses the
transition with "SBR filing is not configured", so nothing is marked
submitted. `SbrFilingStatusListener` handles
`nl.conduction.sbr.filing.status`: a delivered status records the
Digipoort reference in `digipoortReceiptId` and requests `submit`'s
completion; accepted and rejected request `accept` or `reject` with the
errors in `rejectionReason`.

Pressing Submit on a VAT return builds its instance if needed, validates
it and submits it; the return's own state follows its instance.

Alternative considered: keep the log adapter bound and let the transition
succeed. Rejected: that is exactly the "changes a status, sends nothing"
the row describes.

### D4. Say what the connection does

`connections.json` changes `digipoort-sbr` from `available: false` to
`reportedOnly: true`, and shillinq reports its status daily the way
`adopt-connection-registry` does for the three called rows: simulated
while the log adapter answers, configured when integriq's connector is
bound.

## Declarative-vs-imperative decision (ADR-031)

| Behaviour | Path | Rationale |
|---|---|---|
| Filing states | Declarative `XbrlInstance` lifecycle | Exists. |
| When a filing may be submitted | Declarative `requires` on `validate` | The guard is the precondition. |
| Building the instance | Imperative builders | A document transformation, like the other generators. |
| Handing off | Imperative lifecycle action behind the existing port | External transport is integriq's. |
| Status from Digipoort | Imperative listener requesting declared transitions | An event from another app. |

## Seed Data

Adds `XbrlInstance.filingType`, `XbrlInstance.sourceReturnId` and
`BtwAangifte.xbrlInstanceId`. Seed: an `XBRLTaxonomy` record for the
taxonomy release effective for 2026 with the OB aangifte and KvK entry
points; the Q3 2026 return of Bakkerij De Korenbloem from
`tax-vat-return-from-books`; the 2025 annual accounts of "Voorbeeld Bouw
B.V." (small size class).

## Risks / Trade-offs

- [Taxonomy details are exacting] → the builders are tested against the entry point's schema files kept in the repository with the taxonomy record, and the first live filing is a Digipoort pre-production test through integriq.
- [integriq ships later] → instances can be built, validated and downloaded before transport exists; nothing claims submission.

## Migration Plan

No data migration. Existing `XbrlInstance` records stay as they are.
